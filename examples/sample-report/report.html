Findings

Medium 1. Response is not protected against clickjacking

web.headers.missing-frame-protection · https://dragonsmithers.com · confidence confirmed · status open · seen 1×

Neither an `X-Frame-Options` header nor a CSP `frame-ancestors` directive is set, so the page can be embedded in a frame on any site.

Impact. An attacker can overlay the application in an invisible frame and trick a signed-in user into clicking destructive or sensitive actions (clickjacking).

x-frame-optionsabsent
csp-frame-ancestorsabsent

Remediation. Set `Content-Security-Policy: frame-ancestors 'none'` (or `'self'` if framing is required). Keep `X-Frame-Options: DENY` as a fallback for older browsers.

CWE-1021 · A05:2021 · evidence ev_ecb255dc94f5

https://owasp.org/www-project-secure-headers/#x-frame-options
https://owasp.org/www-community/attacks/Clickjacking

Low 2. Cross-Origin-Opener-Policy (COOP) header is missing

web.headers.missing-coop · https://dragonsmithers.com · confidence confirmed · status open · seen 1×

The response does not set `Cross-Origin-Opener-Policy`, so a cross-origin window that opens this document keeps a reference to it.

Impact. Cross-window scripting (XS-Leaks, Spectre-style side channels and window.opener abuse) is easier when the opener relationship is preserved.

Remediation. Set `Cross-Origin-Opener-Policy: same-origin` on HTML responses.

Low 3. HSTS policy does not cover subdomains

web.headers.hsts-missing-include-subdomains · https://dragonsmithers.com · confidence confirmed · status open · seen 1×

The Strict-Transport-Security header does not include the `includeSubDomains` directive, so the policy only protects the exact host that sent it.

Impact. HTTP-only subdomains (staging, legacy portals, mail front-ends) remain reachable over cleartext and can be used to steal cookies scoped to the parent domain.

strict-transport-securitymax-age=31556952

Remediation. Add `includeSubDomains` to the header once every subdomain serves HTTPS: `Strict-Transport-Security: max-age=31536000; includeSubDomains`.

CWE-319 · A02:2021 · evidence ev_ecb255dc94f5

https://owasp.org/www-project-secure-headers/#strict-transport-security

Low 4. X-Content-Type-Options header is missing

web.headers.missing-x-content-type-options · https://dragonsmithers.com · confidence confirmed · status open · seen 1×

The response does not set `X-Content-Type-Options: nosniff`, so some browsers will sniff a body and execute it as a type the server did not declare.

Impact. A user-uploaded file that is served back with a permissive content type can be interpreted as HTML or script, turning a file upload into stored XSS.

x-content-type-optionsabsent

Remediation. Set `X-Content-Type-Options: nosniff` on every response (it is cheap and safe to apply globally).

CWE-16 · A05:2021 · evidence ev_ecb255dc94f5

Info 5. Content-Security-Policy is set with a meta tag only

web.headers.csp-meta-only · https://dragonsmithers.com · confidence confirmed · status open · seen 1×

The page declares its CSP in a <meta http-equiv> tag instead of a response header. Browsers enforce its fetch directives, but ignore frame-ancestors, sandbox and report-uri/report-to in a meta policy.

Impact. Framing control and violation reporting are unavailable; the policy also only starts applying once the tag is parsed.

meta content-security-policydefault-src 'self'; script-src 'self' https://static.cloudflareinsights.com; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' https://cloudflareinsights.com; form-action 'self'; base-uri 'self'; object-src 'none'; frame-src 'none'; upgrade-insecure-requests

Remediation. Where the host allows it, send the policy as a Content-Security-Policy response header. On hosts that cannot set headers (for example GitHub Pages), put the site behind a CDN that can, such as Cloudflare.

CWE-693 · A05:2021 · evidence ev_ecb255dc94f5

https://developer.mozilla.org/en-US/docs/Web/HTML/Element/meta#http-equiv

Info 6. CORS wildcard origin policy is enabled

web.cors.wildcard-origin · https://dragonsmithers.com · confidence confirmed · status open · seen 1×

The endpoint returns `Access-Control-Allow-Origin: *`, so any origin can read its responses. No credentials are shared, so this is only a problem if the response contains data that should not be world-readable.

Impact. Any website can fetch and read this resource on behalf of the visitor (including intranet-only data reachable through the visitor's network position).

access-control-allow-origin*
access-control-allow-credentialsfalse
responsesGET, Origin: null GET

Remediation. If the data is truly public this is acceptable — document it. Otherwise replace the wildcard with an exact origin allow-list and drop `Access-Control-Allow-Credentials` from responses that do not need it.

Info 7. Cross-Origin-Embedder-Policy (COEP) header is missing

web.headers.missing-coep · https://dragonsmithers.com · confidence confirmed · status open · seen 1×

The response does not set `Cross-Origin-Embedder-Policy`. Without COEP the page is not cross-origin isolated, so powerful isolation-based mitigations are unavailable.

Impact. Some browser hardening features (high-precision timers, SharedArrayBuffer) are unavailable and cross-origin reads are less constrained.

Remediation. Set `Cross-Origin-Embedder-Policy: require-corp` once embedded resources opt in via CORP.

Info 10. Permissions-Policy header is missing

web.headers.missing-permissions-policy · https://dragonsmithers.com · confidence confirmed · status open · seen 1×

The response does not restrict powerful browser features. Without a policy, embedded third-party frames and compromised scripts can request camera, microphone, geolocation and similar access.

Impact. Feature access is granted by default to any origin the page embeds, increasing blast radius.

permissions-policyabsent

Remediation. Set `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()` and re-enable only the features the application actually uses.

CWE-693 · A05:2021 · evidence ev_ecb255dc94f5

Methodology

Safe mode: the full non-destructive check set was enabled — DNS records, TLS configuration, TCP service identification, HTTP security configuration and bounded content discovery.

Scope enforcement. Every network action was authorized against the engagement scope before it ran. Out-of-scope or excluded requests were refused and recorded in the audit log rather than retried elsewhere.

Reconnaissance. DNS records, TLS configuration, exposed TCP services and (in scope) hostnames and endpoints were enumerated only for assets covered by the authorized scope.

Configuration review. Responses were graded against the enabled check set: HTTP security headers, cookie attributes, CORS policy, allowed methods and other non-destructive configuration signals.

Evidence capture. HTTP exchanges were stored as redacted, content-hashed evidence records. Findings reference those records by identifier; authorization headers, cookies and credential query parameters are redacted.

Analysis. Findings were normalized against a fixed severity, confidence and proof-of-evidence vocabulary. Re-observations merge into the existing finding instead of creating duplicates.

Limitations

  • Testing was non-destructive: no exploitation, brute force, fuzzing at volume, credential attack or denial-of-service activity was performed. The report therefore does not demonstrate exploitability.
  • Results reflect the state of the systems at the time of testing. Services, configuration and code change, so findings should be re-validated before remediation is considered complete.
  • Only assets explicitly covered by the authorized scope were tested. Any host, path or port outside that scope was not assessed and may hold undiscovered issues.
  • Absence of a finding is not proof that a vulnerability is absent. The checks are bounded by the recorded scope, request budget, timeouts and the enabled check set.
